# Sara Wallet

A cross-platform personal finance wallet. One Supabase backend, one shared
TypeScript package, two clients: a React Native (Expo) app for phones and an
Electron app for the desktop.

```
personal-wallet-monorepo/
├── apps/
│   ├── mobile/     Expo (React Native) client
│   └── desktop/    Electron client (main / preload / renderer)
├── packages/
│   └── shared/     @wallet/shared — client, services, hooks, utils
├── supabase/
│   ├── migrations/ 0001_init.sql, 0002_transfers.sql,
│   │               0003_wallet_currency_guard.sql, 0004_guard_balance_writes.sql
│   ├── tests/      assertions.sql — runnable self-check for the migrations
│   └── apply-all.sql   generated by `pnpm migrations:bundle` (gitignored)
├── scripts/
│   ├── check-sql.py          parses the migrations with the real PostgreSQL grammar
│   ├── check-sql-live.mjs    executes them against PostgreSQL in WASM (PGlite)
│   ├── check-supabase.mjs    verifies the live project: config, keys, schema, RLS
│   └── bundle-migrations.mjs concatenates the migrations into one paste
├── .env.example
├── pnpm-workspace.yaml
└── tsconfig.base.json
```

## Stack

| Layer      | Choice                                                              |
| ---------- | ------------------------------------------------------------------- |
| Mobile     | Expo SDK 51, React Native 0.74, React 18                            |
| Desktop    | Electron 32, electron-vite 2, React 18                              |

| Validation | Hand-rolled guards in `packages/shared/src/utils/validate.ts`        |

## Quick start

### 1. Create the database

Open your Supabase project → **SQL Editor** → **New query**, and run the four
migrations **in order**. Each is idempotent, so re-running is safe.

The easy way is to let the repo concatenate them for you:

```bash
pnpm migrations:bundle      # -> supabase/apply-all.sql
```

That writes a single paste-ready file (generated from `supabase/migrations/`, so
it cannot drift, and gitignored for the same reason). Paste the whole thing into
the SQL Editor and hit **Run** — one paste instead of four, with no chance of
getting the order wrong.

| File                              | What it adds                                                 |
| --------------------------------- | ------------------------------------------------------------ |
| `0001_init.sql`                   | tables, indexes, RLS, balance trigger, `get_monthly_summary`  |
| `0002_transfers.sql`              | wallet-to-wallet transfers, transfer-aware reporting          |
| `0003_wallet_currency_guard.sql`  | refuses a currency change on a wallet that has history        |
| `0004_guard_balance_writes.sql`   | refuses a direct write to `wallets.balance`                   |

They create:

- `wallets` and `transactions` with CHECK constraints and `numeric(18,2)` money
- indexes on `user_id`, `wallet_id`, `date`, plus the composite pairs the app actually queries
- RLS **enabled** on both tables with `SELECT` / `INSERT` / `UPDATE` / `DELETE` policies all pinned to `auth.uid() = user_id`
- `wallets.balance` maintained automatically by a trigger — never write it from a client
- a `handle_new_user` trigger that gives every signup a starter "Cash" wallet
- a `get_monthly_summary` RPC so a month's totals are aggregated in the database
- a `transfer_between_wallets` RPC that writes both ledger legs in one transaction

If you use the Supabase CLI instead:

```bash
supabase link --project-ref <your-ref>
supabase db push
```

#### Then prove it works

There are three layers, and they catch different things.

**0. Confirm the project is actually migrated:**

```bash
pnpm check:supabase
```

This talks to the real project in your `.env` and reports four things: whether
every variable is set and free of `.env.example` placeholders, whether each key
authenticates, whether PostgREST's schema cache knows about the tables and RPCs
the code calls, and whether `anon` is locked out of the ledger. It exits non-zero
with the exact fix when something is wrong.

It exists because of a specific failure that no offline check can catch:

```
{"code":"PGRST205",
 "message":"Could not find the table 'public.transactions' in the schema cache"}
```

That is PostgREST saying it has never seen the table — the migrations have not
been applied. The app code is fine, the keys are fine, and nothing in the client
can fix it. Without this check the symptom looks exactly like a bug.

**1. Run the migrations and the assertions locally** — no Docker, no database:

```bash
pnpm check:sql:live     # 79 assertions, ~1 second
```

This boots PGlite (PostgreSQL compiled to WebAssembly), stands up the few
objects Supabase provides for free, applies all four migrations, and then runs
`supabase/tests/assertions.sql`. It is the check that catches things a parser
cannot — the `0002` migration originally rewrote `get_monthly_summary` with
`create or replace`, which PostgreSQL rejects outright because the rewrite
changes the function's return type. `pnpm check:sql` was perfectly happy with
it; this was not.

The assertions run statements **as the `authenticated` and `anon` roles with a
real JWT subject**, so the RLS policies are exercised rather than inspected —
including that a user cannot read, rename or delete another user's wallet, and
that a direct write to `wallets.balance` is refused.

**2. Run the same assertions against the real project.** Paste
`supabase/tests/assertions.sql` into the SQL Editor and run it. It creates two
throwaway users, drives the balance trigger through every path (insert, amount
edit, direction flip, wallet move, delete), exercises transfers and the currency
guard, reports what it observed, and rolls everything back — so it is safe on a
live project.

```sql
-- read the last result set:
--   assertions | passed | failed | setup_steps | verdict
```

PGlite is not Supabase: it has no PostgREST, no GoTrue, and no extension
catalogue, so `auth.users`, `auth.uid()` and the `anon` / `authenticated` roles
are shimmed by the script and the `pgcrypto` line is skipped (nothing is lost —
the migrations only take `gen_random_uuid()` from it, which is core since
PostgreSQL 13). Treat the local run as the fast first line of defence and the
SQL Editor run as the one that counts.

### 2. Configure credentials

```bash
cp .env.example .env
cp apps/mobile/.env.example apps/mobile/.env
cp apps/desktop/.env.example apps/desktop/.env
```

Fill in the URL and **anon** key from **Project Settings → API** in all three.
Only the anon key belongs in a client bundle; RLS is what protects the rows.

> **Copy-pasting `.env.example` leaves the placeholder keys in place.** They look
> like real JWTs (`eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...`) and are 39 characters
> long instead of ~208, so they authenticate as nobody. `pnpm check:supabase`
> flags them; a plain "it doesn't work" will not.

> Email confirmation is on by default for new Supabase projects. For faster
> local testing, turn it off under **Authentication → Providers → Email**.

### 3. Install and run

```bash
pnpm install

pnpm mobile     # Expo dev server — press i / a, or scan the QR code
pnpm desktop    # Electron window with hot reload
```

After changing a `EXPO_PUBLIC_*` value, restart Expo with a cleared cache:
`npx expo start -c`.

## How the pieces fit together

### `packages/shared`

Everything platform-agnostic lives here. It is shipped as **source**, so Metro
and Vite each compile it with their own settings — no stale `dist/` can ever
diverge from the code you are reading.

```
src/
├── config/supabase.ts      adaptive client (AsyncStorage ⇄ localStorage)
├── types/                  database.ts (Supabase row types), wallet.ts, auth.ts
├── services/               auth.ts, wallet.ts, transaction.ts
├── hooks/                  useAuth.ts, useWallets.ts, useTransactions.ts
├── utils/                  currency.ts, date.ts, errors.ts, validate.ts
└── **/__tests__/           Vitest specs, colocated with the code they cover
```

**Services never throw raw Supabase errors.** Everything funnels through
`toAppError()` and comes out as an `AppError` with a stable `code`, so both UIs
switch on the same values.

**Hooks own no formatting.** They return plain data and `AppError` messages;
screens decide how to render.

### The adaptive Supabase client

`packages/shared/src/config/supabase.ts` resolves its storage engine at runtime:

1. an adapter passed to `configureSupabase({ storage })`
2. `globalThis.__WALLET_STORAGE__`
3. `AsyncStorage` on React Native — loaded through an indirect `require` that
   web bundlers cannot statically analyse
4. `localStorage` in the Electron renderer
5. an in-memory adapter as a last resort

Both apps call `configureSupabase()` once, before React mounts. Services then
use `getSupabase()` — or the `supabase` proxy, which forwards every property to
the configured client.

### Balances are derived, never written

`wallets.balance` is maintained by the `tg_transactions_apply_balance` trigger
on `transactions`. Adding, editing, moving or deleting a transaction moves the
balance in the same database transaction.

Consequences worth knowing:

- **The database enforces this, not just the client.** `wallets_update_own`
  permits UPDATE on every column of your own row, `balance` included — so a
  client talking to PostgREST directly could previously just
  `PATCH {"balance": 999999}`. `0004` closes that: `apply_wallet_delta` raises a
  transaction-local flag and a guard trigger requires it, so only the ledger
  trigger may move the figure. `updateWallet()` still refuses to send it.
- `openingBalance` is only written at wallet-creation time, where it is a plain
  `INSERT` and no delta has been applied yet. That remains allowed — it is a real
  feature, and the ledger is correct from that moment on.
- After any transaction mutation the hooks re-read the wallet list, so the UI
  shows the server's figure rather than a local guess.

### Transfers are one operation, not two

A wallet-to-wallet transfer is two ledger rows that must both exist or neither.
Two independent client inserts can half-fail — the money leaves one wallet and
never arrives in the other, with no error to show for it. So the pair is written
by `transfer_between_wallets()` in a single database transaction, and both legs
carry the same `transfer_group_id`.

That group id is what lets the app treat the pair as one unit:

- a trigger refuses any `UPDATE` to a leg, so a transfer can only be deleted and
  re-recorded — editing one leg would leave the pair unbalanced
- deleting either leg deletes its sibling, and the balance trigger then puts
  both wallets back exactly where they started
- `get_monthly_summary` excludes transfer legs from `income` / `expense` / `net`
  and reports them separately as `transfer_volume`, so moving money between your
  own wallets does not inflate the month
- cross-currency transfers are refused rather than assumed to be 1:1, because
  the app does not model exchange rates

### A wallet cannot change currency once it has history

`wallets.balance` is a bare `numeric` with no currency attached, so changing a
wallet's currency silently reinterprets the number: 50,000 MMK becomes 50,000
USD and nothing in the ledger records a conversion. `0003` adds a trigger that
allows the change only while the wallet is empty *and* has no transactions.

### The ledger pages, searches and scopes by month

`useTransactions` used to fetch a fixed 50 rows and stop. A user with 300
transactions saw the newest 50 and was never told the rest existed — there was
no count, no "load more", and no way to reach them. That is fixed:

- **`getTransactionsPage()`** is now the single read path. It asks for
  `limit + 1` rows and reports `hasMore` from whether the extra one arrived, so
  knowing whether another page exists costs one row instead of a second
  `count=exact` round trip. `limit` is clamped to `MAX_PAGE_SIZE` (200) so a
  mistyped value cannot ask for the whole table.
- **The sort is total.** Ordering is `date`, then `created_at`, then `id`.
  `date` is a `date` column, so a busy day produces many ties; with an unstable
  sort the database may return them in a different order for each page, and
  offset paging then repeats some rows and skips others. `id` is unique, which
  makes the order total and the paging correct.
- **Search is escaped twice.** `searchPattern()` backslash-escapes the LIKE
  wildcards `%` and `_` so they match literally, then wraps the whole value in
  double quotes so PostgREST's `or=(...)` grammar treats commas and parentheses
  as text rather than as separators. Both layers matter: without the quotes, a
  search for `lunch, coffee` is parsed as a second filter branch and rejected.
- **Range bounds are reduced to `YYYY-MM-DD`.** `assertIsoDate` returns a full
  ISO instant, and letting the server decide which calendar day that instant
  falls on makes the answer depend on the server's timezone — a local midnight
  in Yangon is the previous day in UTC. `date` columns have no zone, so the
  bound keeps the day it falls on locally.
- **Month navigation drives the whole dashboard.** The summary tiles, the
  category breakdown and the list all follow the selected month; an "All time"
  toggle drops the date bounds when you want the full history. `LedgerControls`
  in `@wallet/shared` holds the month, scope, search and category filters in one
  object, so both clients render the same bar and neither can drift.
- **Duplicate rows are dropped on merge.** If a write lands between two page
  requests the page boundary shifts and the last row of page 1 reappears at the
  top of page 2. `mergeTransactionPages()` de-duplicates by `id`, which turns a
  React duplicate-key warning into a non-event.

One consequence worth knowing: a mutation calls `refresh()`, which reloads
page 1 and resets the pagination. Deleting a row you loaded from page 3 puts you
back at the top of the list. Correct, if slightly abrupt.

### Electron security posture

`apps/desktop/src/main/index.ts`:

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`
- the preload exposes exactly six IPC channels via `contextBridge` — never `ipcRenderer`
- `setWindowOpenHandler` and `will-navigate` deny in-app navigation and hand
  external URLs to the system browser, restricted to `https:` / `http:` / `mailto:`
- a strict CSP header is injected in packaged builds, and skipped in dev so
  Vite's HMR websocket still works
- every permission request (camera, geolocation, …) is denied by default

## Verification

```bash
pnpm typecheck        # every workspace, in parallel
pnpm test             # Vitest, in packages/shared — 352 specs
pnpm check:sql        # parse every migration with the real PostgreSQL grammar
pnpm check:sql:live   # execute every migration + 79 behavioural assertions
pnpm check:supabase   # verify the live project in .env is migrated and locked down
```

`pnpm test` runs the specs colocated under `packages/shared/src/**/__tests__/`.
They deliberately cover the parts that are hard to reach any other way: the
storage-detection chain (whose interesting branches only exist on the *other*
platform), the currency formatter's no-ICU fallback path, and the `AppError`
classification table.

`pnpm check:sql` needs `pglast`:

```bash
python -m venv .venv-sql
.venv-sql/Scripts/pip install pglast   # Windows
# .venv-sql/bin/pip install pglast     # macOS / Linux
```

The script re-runs itself inside `.venv-sql` (or `.venv`) when the Python that
launched it has no `pglast`, so `pnpm check:sql` works without any PATH
juggling.

`pnpm check:sql:live` needs `@electric-sql/pglite`, which is a normal
devDependency — `pnpm install` is enough. (If installing into the workspace is
blocked in your environment, `npm install --prefix .tools @electric-sql/pglite`
works instead; the script looks there as a fallback.)

Together they mean the SQL is checked at three levels: it parses, it applies to a
clean database, and the trigger arithmetic actually adds up.

## Deliberate deviations from the original folder sketch

1. **`apps/mobile/App.tsx` instead of an Expo Router `app/` tree.** The sketch
   listed both an `app/_layout.tsx` router tree *and* an `App.tsx` entry — Expo
   uses one or the other, never both. The `App.tsx` + `src/screens/` variant is
   what shipped, because it is self-contained and matches the STEP 3 brief. To
   switch to Expo Router: `npx expo install expo-router react-native-screens
   react-native-safe-area-context expo-linking`, set `"main": "expo-router/entry"`,
   add `"scheme"` to `app.json`, then move each file from `src/screens/` into
   `app/` and add a root `_layout.tsx`. The screens are presentational, so the
   move is mechanical.
2. **`utils/errors.ts` and `utils/validate.ts` are new.** The brief asked for
   "strict error handling" and typed DTOs; these two files are where that lives.
3. **`src/shared/ipc.ts` in the desktop app** is the type contract shared by the
   main process, the preload script and the renderer, so the three cannot drift.
4. **`types/category.ts` is new, and replaces two copies of the same array.**
   `INCOME_CATEGORIES` and `EXPENSE_CATEGORIES` were duplicated verbatim in
   `AddTransactionSheet.tsx` and `AddTransactionDialog.tsx` — the classic way a
   picker on one platform ends up offering a category the other cannot filter
   by. They now live in `@wallet/shared` alongside `ALL_CATEGORIES` (the deduped
   union, including the `Transfer` category the RPC writes) and
   `categoriesForType()`.

## A note on colours

Money in is **red** and money out is **green**, following the Chinese-market
convention where a rising figure is red. Both values live in
`apps/mobile/src/theme.ts` and `apps/desktop/src/renderer/src/styles/global.css`
— swap the two `--income` / `--expense` values to flip it.
